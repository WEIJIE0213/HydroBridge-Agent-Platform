# 水利科技成果转化 Agent 面试题库

> 2026-10-23 修订。按当前 `3.1.0-three-business-tools` 实现核对，保留最新材料的 Q1—Q39，补充 Q40 成果评价、Q41 独立需求分析。回答按面试口述组织，证据与边界放在必要的位置。历史检索指标来自已有验收文件，不代表这次改造重新通过了运行验证；本次未运行测试或重新评测。

开场可以这样说：**一个主 Agent 负责选择业务动作，三个业务子图负责执行；子图返回结果后，Agent 再决定继续、向用户澄清，还是结束。**

## 一、项目整体与 Agent 架构

### Q1 ★ 先介绍一下你的项目

这个项目面向水利科技成果推广和工程选型，主要解决成果资料分散、工程需求难以匹配、资料查询依赖人工的问题。

我把功能分成三组：**成果搜寻与评价**负责联网发现、入库分流和单项成果评价；**需求分析与匹配**负责整理工程需求、澄清条件和推荐候选；**成果答疑问答**负责库内检索、指标追问和成果对比。

架构采用 LangGraph 的一个主 Agent 加三个业务子图。PostgreSQL 保存业务数据和检查点，Elasticsearch 做混合检索，FastAPI 接入请求，Celery 执行任务，SSE 展示过程。系统提供的是带依据的决策支持，最终工程适用性仍需要现场和专家复核。

### Q2 ★ 你的 Agent 整体架构是什么样的？

分为决策层和执行层。主循环是 `agent → dispatch → 业务子图 → collect → agent`：模型选动作，程序校验并调度，子图执行，保存结果后再交给模型。模型停止调用时进入 `respond`，汇总已完成的报告和引用。

三个模型可见工具分别是 `research_achievements`、`match_achievements`、`ask_achievements`，对应三个独立编译的业务子图。子图内部用固定节点、条件分支和必要的检索循环处理业务；子图的 `END` 只是返回主图。

三个子图共享状态和父图检查点。主 Agent 统一决定先做什么、后做什么，具体业务步骤由各子图控制。

### Q3 一次请求从进来到返回，完整流程是什么？

FastAPI 校验身份和输入，创建会话消息及运行记录，提交数据库后把任务交给 Celery，并返回 Run ID。Worker 加载需求画像、候选列表和历史摘要，再运行 LangGraph。

例如“匹配低功耗水位监测成果，再比较前两项”，Agent 可以先调用匹配工具，读取排序和真实成果 ID，再调用问答工具对比。每项业务结果独立保存，最终汇总回答，过程通过 SSE 推送。

如果需要审核或关键条件澄清，子图会通过 `interrupt` 暂停，用户提交后恢复同一次运行。实际调用顺序仍取决于模型决策，不能把这个例子当作所有请求的固定路径。

### Q4 ★ 为什么用单 Agent，不用多 Agent？

当前三个功能共用知识库、需求画像和会话信息，功能内部的业务顺序也比较清楚。使用一个主 Agent 统一调度，可以减少多个规划者之间的任务分配、状态同步和结果冲突。

子图里虽然有需求分析、评价、核验等专业步骤，但它们没有各自独立的自主规划循环。以后新增能力，可以在对应子图增加模式；如果确实是新的业务边界，再增加工具和子图，同时补齐状态、权限、持久化与验证设计。

### Q5 ★ 项目里既有 workflow 又有 ReAct，不矛盾吗？

不矛盾，它们描述的是不同层次的控制方式。项目外层采用 ReAct 式的“决策、行动、观察、再决策”循环，内层用 workflow 执行相对确定的业务步骤。

例如先匹配还是先查资料由主 Agent 决定；匹配内部的解析、过滤、召回、重排和约束核验，由代码确定顺序。问答子图还允许根据证据不足继续检索。

并不是调用一次大模型就叫 ReAct。需求解析和信息抽取属于流程中的模型步骤；关键要看是否存在根据动作结果继续决策的闭环。

### Q6 为什么用 LangGraph，而不是直接写 Python？

主要因为项目同时需要共享状态、条件分支、循环和人工介入后的恢复。LangGraph 用 State 传递数据，用边控制流程，用 Checkpointer 保存执行状态，用 `interrupt` 和 `Command(resume=...)` 处理暂停与继续。

这些也能用 Python 自己实现，但要维护更多状态转换和恢复逻辑。框架负责图执行，应用仍然负责鉴权、业务事务、任务入队和幂等，不能把这些责任都交给检查点。

## 二、LangGraph 与工具调用

### Q7 ★ ReAct 和 Tool Calling 有什么区别？项目怎么结合？

Tool Calling 是调用机制：模型根据工具 Schema 返回结构化的工具名和参数。ReAct 是运行方式：执行动作，观察结果，再决定下一步。

项目使用模型原生 Function Calling 选择动作，但没有直接使用预置 `ToolNode` 或 `ToolMessage` 消息循环。这里由自定义 `dispatch` 调度业务子图，`collect` 把结果写回 State；下一轮将紧凑的结果观察传给模型。

这同样形成了 Agent 闭环。采用自定义调度是为了接入业务记录、权限范围、人工中断和动作幂等，不需要为了名称一致而换成另一种节点。

### Q8 工具怎么设计的？为什么顶层只有三个？

三个工具对应三个业务功能，内部用模式区分具体操作：

| 工具 | 模式 | 业务含义 |
|---|---|---|
| `research_achievements` | `research` / `evaluate` | 联网搜寻入库 / 单项成果评价 |
| `match_achievements` | `analyze` / `match` / `refine` | 独立分析 / 分析并匹配 / 局部修改已有需求 |
| `ask_achievements` | `search` / `detail` / `compare` | 原文答疑 / 结构化概览 / 多成果对比 |

`refine` 可以通过 `match_after_refine` 选择更新后是否匹配。联网搜索、重排等底层步骤留在子图内部。参数先经过 Pydantic 和模式校验，不合法时不会执行业务操作，而是反馈给 Agent 修正。内部保留细分动作名用于路由和旧检查点兼容，但它们不再是额外的模型可见工具。

### Q9 LangGraph 的 State 里存什么？

主要有任务身份和原始目标、需求画像、候选列表、动作状态、证据以及最终回答。原始目标独立保存，避免某一次检索查询覆盖整轮任务。

候选列表 `active_candidates` 保存序号、成果 ID 和标题；`scope_limit` 保存用户明确限定的范围，二者分开管理，候选排序本身不会授予权限。

原件放在对象存储，但 State 中仍保存必要的原文片段和完整动作结果，用于检查点恢复和引用核对。发送给主模型的是压缩后的观察，因此不能说 State 只存 ID，也不能把输入压缩等同于删除审计数据。

### Q10 ★ Checkpoint 和 interrupt 怎么用？与聊天记录有什么区别？

聊天记录保存说过什么，Checkpoint 保存一次图运行到了哪里，以及当时的 State。普通新追问会创建新 Run；只有审核或澄清等中断，才恢复原 Run。

项目将检查点存入 PostgreSQL，配置中的 `thread_id` 使用运行 ID。人工处理节点先调用 `interrupt`，恢复时传入 `Command(resume=...)`。中断节点可能从头重新执行，所以不能在中断之前放无保护的重复写操作。

业务写入还需要动作 ID、记录绑定和幂等校验。检查点和业务结果不属于同一个数据库事务，不能据此承诺所有外部副作用都只执行一次。

### Q11 多轮对话如何理解“第二个成果”？

系统在跨轮状态里保存最近展示的有序候选列表。模型把“第二个”解释为序号 2，调用工具时传入 `achievement_ranks=[2]`；服务端从列表确定真实成果 ID，再检查限定范围和访问权限。

查看某项详情、比较前两项不会重排这个列表；新的匹配或不指定成果 ID 的检索会更新列表，并在回答中展示当前序号。

这把序号到 ID 的映射交给了程序，但自然语言指代仍需要模型理解。如果出现多个历史列表、“它”指向不清，或者当前没有有效序号，就需要澄清，不能宣称所有指代都能无歧义解析。

### Q12 ★ 有没有做上下文压缩？

有，主要是结构化记忆、历史增量摘要和动作观察压缩。需求约束、候选 ID 和范围单独保存；较早的完整轮次在超出预算后做摘要，近期消息按预算保留；主 Agent 接收动作报告的短摘录，不反复读取完整报告。

默认历史摘要与近期消息合计使用约 6000 的估算 token 预算，摘要预算 1000，近期边界按 8 条消息控制。摘要失败时保留旧摘要和覆盖位置，再裁剪近期窗口。

这里用的是字符估算，不是供应商 tokenizer，也不是所有模型输入的总硬上限。原始消息、引用和完整结果仍保留，三个子图也没有做完全独立的私有状态隔离。摘要只帮助理解，不作为事实证据或约束来源。

### Q13 工具调用失败或模型循环怎么办？

分情况处理。工具名、参数和候选序号不合法时，先拦截并把错误作为观察交回 Agent；对象不存在或不在可访问范围内时，提示重新选择。修正也计入动作次数，重复相同调用会被停止。

基础设施异常不能一概交给模型“自动修复”。ES 客户端有有限重试，可配置本地检索降级；未处理异常由运行层记录失败，已经保存的业务结果保留。LLM 调用没有统一的自动重试保证。

主循环默认最多 12 个动作，问答内部最多两轮检索，另有图递归限制和运行总超时。达到限制时返回已有结果和停止原因，不把失败描述成成功。

## 三、成果知识库与混合检索

### Q14 成果知识库怎么构建？

有联网搜寻和本地资料导入两条路径。联网搜寻由 Agent 进入业务子图，搜索和筛选来源，调用模型抽取成果字段与证据，再根据质量规则自动入库、进入审核或拒绝。

本地资料则先通过离线解析和整理流程形成数据包，处理文件去重、文本提取和成果关联，再由导入程序写入数据库。当前导入程序不是把所有本地文件重新交给模型抽取，也不属于每次聊天都会执行的子图步骤。

两条路径最终共用 PostgreSQL 成果数据、MinIO 原件和 Outbox 索引更新机制，再生成片段与向量进入 Elasticsearch。

### Q15 大模型抽取成果信息，怎么防止抽错？

先用结构化 Schema 约束字段类型，再要求关键字段附来源和证据，原文没有的指标留空，不允许凭经验补数值。后续检查完整性、来源质量、主题和时间范围，并按分数与风险分流。

当前默认低于 60 分或触发硬性拒绝条件就拒绝；60 到不足 80 分进入审核；达到 80 分但存在风险也需要审核；达到 80 分且无相应风险才自动入库。

Schema 能检查格式，不能证明抽取语义正确。当前入库抽取没有对所有字段实施问答链路那样的逐字引文校验，来源冲突和重要指标仍需要复核。

### Q16 ★ 为什么使用 PostgreSQL 和 Elasticsearch？如何保证一致？

PostgreSQL 是业务权威数据源，保存成果、审批状态、权限、版本和运行记录；Elasticsearch 保存派生的全文与向量索引，负责快速找候选。

成果变更与 Outbox 事件在同一个 PostgreSQL 事务中提交，后台消费事件并幂等更新索引，失败可以重试。检索结果返回前，再回 PostgreSQL 检查权限、审批状态、版本和片段哈希。

这样提供的是最终一致性。复核可以避免旧索引内容被用作证据，但同步有延迟时，仍可能暂时查不到最新资料。

### Q17 文档怎么切 Chunk？

先按成果字段和原始文档片段划分，避免把技术原理、应用场景、指标和不同来源混成一块。长内容默认约 700 字符一块，重叠 100 字符，优先在后半段的句号、分号或换行处断开。

片段记录成果 ID、版本、字段、内容哈希和位置；原件来源还可带文档 ID、页码或行号，便于引用核对。

700/100 是工程配置，不是已经证明的最优值。字符数不等于 token 数，位置偏移也通常相对于字段或来源片段，不能都当作整份文件的全局位置。

### Q18 ★ BM25 和向量检索有什么区别？为什么混合？

BM25 主要依靠词项匹配和统计，适合专业术语、设备名称和具体指标；向量检索比较语义表示，适合需求与成果资料措辞不同的情况。

例如用户描述“巡检人手不足”，资料可能写“远程自动监测”，向量召回能补充字面检索覆盖不到的候选；但语义相近并不等于满足工程条件。

因此采用双路召回、融合和重排，同时保留元数据过滤及约束核验。两路互补是设计理由，是否有收益还要看同一批查询上的实际结果，不能说混合在每个指标上都必然更好。

### Q19 HNSW 是什么？项目里怎么用？

HNSW 是基于多层近邻图的近似最近邻检索方法。查询先在较稀疏的上层接近相关区域，再逐层细化，减少与全部向量逐一比较的计算量，但可能损失部分召回。

项目在 ES 的 `dense_vector` 上使用 `int8_hnsw`，默认 `m=16`、`ef_construction=100`，向量检索 `k=60`、`num_candidates=180`。前两项影响建图和资源开销，后者影响查询的搜索范围。

这些是当前配置，不是专门调优后证明最好的参数；需要结合数据量、过滤条件、召回与延迟评估。

### Q20 ★ RRF 是什么？为什么不直接把分数加权？

RRF 是倒数排名融合。项目按片段 ID 合并两路结果，一个片段的融合分是各路 `1 / (60 + 排名)` 之和，同一路重复片段只计算一次。

BM25 分数和向量相似度的尺度不同，直接相加很难解释权重的含义。RRF 使用排名，避免直接比较原始分数，实现也比较简单。

它并不意味着无需调参。平滑常数、每路候选数量和后续截断都会影响结果；经过适当校准的分数融合也是可选方案，只是当前项目采用 RRF。

### Q21 有了 RRF，为什么还需要 Reranker？

RRF 利用已有排名融合，不重新联合分析查询和候选文本。重排模型把查询与候选片段一起输入，进一步判断相关程度。

项目用 BGE-M3 生成向量，用 BGE-reranker-v2-m3 重排。先召回有限候选，再对“标题加片段”计算重排分，避免对全库执行昂贵的交叉编码。

成果最终取候选片段中的最高分作为相关度，每项保留靠前的证据片段。重排不能找回召回阶段完全遗漏的成果，而且会增加延迟，所以要同时观察质量收益和成本。

## 四、需求分析与匹配

### Q22 ★ 需求匹配的完整流程是什么？

先把需求整理成画像，缺少关键条件时澄清。然后在 ES 两路检索中加入审核状态、组织权限、指定成果范围和可用的成熟度等过滤条件，执行 BM25 与向量召回，再用 RRF 融合。

候选返回后，回 PostgreSQL 核验权限、版本及片段哈希，按成果分组，再对候选片段重排，以每项成果最高片段分排序，最多返回 10 项。

最后逐条检查硬约束，给出满足、不满足或未知，以及原文依据。准确地说，ES 路径是先在索引中过滤，再回数据库复核，并非先从数据库取出全部合格成果才开始 ES 检索。

### Q23 自然语言需求会提取成什么格式？

会转成需求标题、规范化描述、工程场景、核心问题、目标、硬约束、软偏好、已知条件和缺失项。

例如用户说“山区水库，必须支持远程水位传输，功耗尽量低”，可以提取场景为山区水库水位监测，远程传输作为明确要求，低功耗作为偏好。通信覆盖和精度如果会实质影响匹配，需要进一步确认。

不能自行增加“低维护”，也不能把“尽量低”写成某个功耗上限。解析结果仍可能误解用户，所以画像和后续修改应能被核对。

### Q24 为什么不能全部交给向量检索？

语义相似回答的是“内容是否相关”，不是“条件是否满足”。某项成果可能与问题高度相关，却明确达不到所需成熟度，或者没有资料证明能适应低温环境。

能明确判断的元数据条件先过滤，描述性条件再依据原文核验。对于成熟度未知等情况，不能直接按不满足排除，应保留待确认。

最终把相关度和约束状态分开展示，用户才能看出哪些成果值得进一步了解、哪些条件还缺证据。

### Q25 ★ 三态约束核验怎么实现？

先用规则核验可直接比较的字段。例如要求 TRL 不低于 7，成果给出 TRL 8，且有对应字段证据，可以判满足。规则不能确定的保留未知。

配置了模型时，默认对前 5 项成果中的未知约束补充取证。模型必须返回片段 ID 和逐字引文；程序检查片段归属、引文存在及最小长度，不合法就保留未知。模型不能覆盖已有的明确规则结论。

这里还没有通用单位换算。有效引文只说明文字存在，不能完全证明判断正确，因此未知要明确展示，关键条件仍需复核。

### Q26 用户需求不完整，先匹配还是先追问？

看缺失信息是否会实质改变结果。需求分析会返回缺失项、澄清问题和 `requires_clarification`；需要澄清时进入 `interrupt`，保留当前画像和业务关联。

用户编辑补充后，当前澄清流程会重新解析更新后的需求描述；批准现有内容则继续原任务。独立分析走到报告，匹配任务继续检索和核验。

这与后续明确修改已有需求的 `refine` 不同：`refine` 使用字段补丁合并。不能把所有澄清恢复都描述成程序自动做无损字段合并，也不能说澄清后一定启动匹配。

### Q27 最终排序是大模型打分吗？

需求匹配主要使用重排相关度排序，有明确硬约束不满足的成果排到后面，未知项单独标注。规则核验和必要的模型证据判断共同生成约束状态。

这里的 0—100 分表示检索相关度，不是适用概率，也不是工程可行性的综合评分。当前没有额外保证“满足”一定排在所有“未知”之前。

独立成果评价是另一条业务路径，会输出六维评价分；不能把它和针对具体需求的检索排序混为一谈。

## 五、成果答疑问答与上下文

### Q28 ★ Agentic RAG 和普通固定 RAG 有什么区别？

项目在两层根据结果继续行动。外层 Agent 可以先匹配、再对比或补充问答；内层问答子图在限定范围内检索、生成带证据的回答，再检查引文与充分性。

如果证据不足，模型给出缺口和新的查询，程序在查询不重复且未达到上限时再检索。当前最多两轮；没有新查询也会提前停止。

到上限仍不足时应说明“本次检索证据不足”，而不是断言“整个资料库里没有”。候选序号是在工具分派前解析的，问答子图内部没有额外的通用指代解析节点。

### Q29 ★ 怎么控制幻觉？

检索阶段用混合召回和重排找候选，并回 PostgreSQL 核对权限与版本。生成阶段要求事实性回答绑定片段 ID 和逐字引用，不允许补写成本、指标或适用条件。

校验阶段检查片段是否来自本轮证据、引文是否存在；证据不足时补检索或明确保留未知。历史摘要不能代替本轮证据。

这些措施用于降低无依据输出风险并增强可追溯性。目前没有完整实验量化“幻觉降低了多少”，而且引文真实也可能被错误概括，不能承诺消除幻觉。

### Q30 “预算放宽一点，重新匹配”怎么处理？

如果原需求有明确预算上限，“放宽一点”仍缺少新边界，Agent 应先询问具体金额；在没有明确条件时不猜一个数替用户修改。

用户给出明确金额后，使用 `match_achievements(mode=refine)`，只传预算对应的字段补丁。程序按约束键合并，未传字段保持不变，再按需执行匹配；一个约束键的值整体替换，因此预算对象里的单位等信息也要正确保留。

报告会列出本轮改动并展示新候选。字段合并是确定的，但自然语言到字段和值的对应仍由模型理解，不能保证理解永远正确，也还没有自动生成完整的新旧排名差异报告。

## 六、评测与工程实践

### Q31 ★ 项目实际做过什么评测？“Recall@10 达到 92%”可靠吗？

现有文件不支持这个说法。能核对的是已有全库检索验收：在 3860 项成果、30266 个片段上，使用 40 条固定的开发验收问题，比较四种检索方式。

混合检索加重排的 Hit@1 是 80%，Hit@5 和 Hit@10 都是 100%，MRR@10 约 0.8812。但标签没有经过独立专家穷尽标注，因此不能把 Hit 当成完整相关集合的 Recall。

这些记录评测的是检索服务，不包括需求解析、三态核验、答案生成和新 Agent 的完整闭环。当前应使用已有指标及其范围，不编造 92%、专家标注规模或分场景评测结果。

### Q32 Recall@10 和 Hit@10 有什么区别？

Hit@10 看前十项中是否至少命中一个标注相关成果；Recall@10 看前十项覆盖了相关集合中的多少项，再对查询取平均。

例如一条需求有五项相关成果，只找到一项，这条查询的 Hit 是 1，Recall 是 20%。二者回答的问题不同，不能互换。

当前全库验收标签主要用于检查指定目标能否被找到，因此报告 Hit@K 和 MRR。以后补齐可靠的相关集合，才适合用 Recall 讨论候选覆盖率。

### Q33 怎么判断混合检索是否比单路更好？

固定语料、问题、标签和 TopK，比较 BM25、纯向量、RRF 混合以及混合加重排，同时看命中率、首个正确结果位置和延迟。

已有 40 条验收记录如下。这组数据中，纯向量的 MRR 高于未重排的混合检索，所以不能简单说每加一个模块都会提升。加重排后 MRR 进一步提高，但延迟也明显增加。

| 方法 | Hit@1 | Hit@5 | Hit@10 | MRR@10 | 检索耗时中位数 |
|---|---:|---:|---:|---:|---:|
| BM25 | 67.5% | 92.5% | 95.0% | 0.7958 | 93 ms |
| BGE 向量 | 80.0% | 97.5% | 97.5% | 0.8717 | 104 ms |
| RRF 混合 | 72.5% | 90.0% | 97.5% | 0.8113 | 167 ms |
| 混合加重排 | 80.0% | 100% | 100% | 0.8812 | 1540 ms |

这些是历史检索调用数据，不是本次改造的端到端耗时或并发能力。

### Q34 链路较长，延迟怎么控制？

按阶段缩小处理范围。ES 用 BM25 和 HNSW 召回，RRF 合并排名，重排只处理召回候选；匹配中的模型补充核验默认限制在前 5 项成果，问答限制补检索轮数。

历史上下文和动作结果也控制输入长度，避免每次传完整报告。耗时业务交给 Celery，通过 SSE 持续展示进度。

异步改善请求处理和使用体验，不会让模型计算本身更快。应结合分阶段延迟和 token 记录定位瓶颈，不能只凭架构推导出性能提升比例。

### Q35 为什么使用 Celery 和 SSE？

联网搜寻、抽取、匹配和人工处理都可能超过普通请求的等待时间。FastAPI 负责接收请求并创建运行记录，Celery Worker 执行业务，减少长时间占用请求连接的需要。

节点执行时发布事件，前端通过 SSE 展示进度；Run 状态和结果保存在数据库，刷新后仍可以查询。人工审核期间通过检查点等待，用户提交后再入队恢复。

Celery 不等于任务绝不重复，因此仍要维护运行状态、动作幂等和失败记录。

### Q36 Elasticsearch 不可用怎么办？

客户端对部分连接和超时问题进行有限重试。配置允许时，ES 检索失败会转本地检索；否则错误上交运行层并记录失败。

本次已把降级信息传到匹配和问答报告，即使本地检索没有结果也保留提示。约束补充取证失败时，会说明限制，使用已有片段，无法判定的继续保持未知。

本地降级不代表排序质量、覆盖和速度等同于 ES；数据库或模型服务也不可用时，更不能承诺仍能回答。服务恢复后应重新查询，不能让模型把失败补成事实。

## 七、深挖与补充业务问题

### Q37 ★ 这个项目最难的技术问题是什么？

我认为最难的是让“检索相关”与“工程适用”之间的差距能够被看见。需求往往不完整，成果资料的指标、单位和应用条件也不统一。

我把链路拆成需求结构化、候选检索与排序、硬约束核验三个阶段。能直接比较的用规则，不能直接比较的查原文，证据不足就保留未知，并把依据和缺口放到结果里。

这样有助于定位推荐理由和待核实项，但还不能自动完成工程适用性证明。单位标准化、逐项证据质量和专家评测仍是后续重点。

### Q38 ★ 听起来是 RAG 加业务代码，Agent 体现在哪里？

Agent 体现在根据目标和已有结果动态选择动作。模型可以先匹配，再取证比较，也可以先查到明确成果后再做评价；子图结束后回到主 Agent，由它决定是否继续。

例如“找低功耗水位监测方案并比较前两项的维护成本”，匹配提供有序候选，问答再在指定成果范围内找成本依据。证据不足就继续取证或明确缺口。

子图内部把解析、检索和核验组织为可控流程，外层保留动态决策。这就是项目采用的单 Agent 加业务子图，而不是几个互不关联的一次性接口。

### Q39 如果继续改进，会优先做什么？

第一是建立更统一的工程约束字段、单位和数值范围规则，减少同义字段及单位不一致。第二是引入专家标注，分别评估检索覆盖、约束判断、引用支持度和最终推荐质量。

第三是补齐这次改造的运行验证，包括复合请求、明确与模糊的需求修改、跨轮指代、人工恢复和服务降级。当前只完成了代码与文档修改及静态检查，不能把它们当作端到端验收。

成本优化则基于真实调用数据再做，例如调整候选数量、模型调用和缓存，而不是预先承诺某个下降比例。

### Q40 成果评价与需求匹配有什么区别？

成果评价看一项成果本身的材料和技术基础；需求匹配看它与某条工程需求是否相关、约束是否有证据满足。因此评价不需要先绑定需求。

目前通过成果工具的 `evaluate` 模式唯一定位对象，检查权限，生成创新性、有效性、成熟度、证据充分性、推广价值、经济与实施可行性六维评价，并保存版本、评分标准快照和资料缺口。

当前评价主要依据结构化资料，核验以维度完整和分数范围为主，没有实现逐维分数的充分原文论证，也不能称为专家认证。入库置信度、成果评价分和需求检索相关度是三个不同概念。

### Q41 为什么保留独立需求分析？怎么调用和保存？

用户有时只是希望整理工程问题，还没有准备开始选型。所以使用 `match_achievements(mode=analyze)`，完成需求画像和必要澄清后生成报告，不进入匹配节点。

它与匹配共用需求解析能力，区别在于后续路由。分析结果会保存到需求和规范化记录，关联本次运行，后续可以继续修改或明确请求匹配。

如果只是局部调整已有需求，可以用 `refine` 并关闭 `match_after_refine`。这样独立需求分析仍属于第二个业务功能，不需要再增加第四个顶层工具。
